# Automatic cooking/alchemy tool reader

The Tool reader includes **ESTIMATED DURA** alongside verified durability. For the confirmed active tool: estimate = max(0, verified − floor(seconds since read / seconds per use)). It uses observed pace when available, otherwise the configured craft speed; at one use per second this is exactly verified minus integer age. Unused tools do not decay. Estimates assume continued crafting even when capture is paused, stay clearly marked with ≈, and never replace verified values or feed loot counts. The existing visible-window refresh updates them without another OCR scan, worker or timer.

rc.4 adds quote-safe OCR-row parsing, a wider vertical search band and supplemental gold-bar/character-box localization. A numeric field can be found even when Tesseract merges it with a long name. The existing label band remains necessary for low/empty bars; verified locators are merged and conflicting values stay uncertain. The work budget remains six seconds. In two saved live layouts, the updated path recovered 2,910/3,000 and 2,287/3,000 that were missing from the prior result. This is targeted regression evidence, not complete live coverage.

Automatic tool discovery is enabled by default. Show the game in front with utensil labels visible; no capture box is required. The main window shows readable counters before active-tool confirmation. Use **VIEW TOOLS** for verified durability, last-read ages and clear finding/confirming/tracking/paused states. Manual region OCR remains an optional fallback in Settings.

The reader finds a likely character anchor from paired in-world red/blue bars, with screen center as a search prior when those bars are absent. It reads a narrow band above that anchor at higher resolution, then automatically isolates numeric fractions for two focused OCR reads. It searches outward when needed and can use an OCR-detected **Place Mode** button as a fallback reference. No rearrangement of the game's UI is required.

The character anchor found more candidate labels than the Place Mode band in the three private test frames, with similar narrow-scan time (~0.6–0.7 seconds versus ~1.6–2.2 seconds for whole-frame sparse OCR). These are small discovery measurements, not an FPS comparison or complete accuracy benchmark. The final focused-number path recovered 95/3000 and then 82/3000 on moved-camera captures while another tool remained 2472/3000. Names obscured by overlapping labels are explicitly marked as partly covered.

## Active-tool evidence

Position prioritizes the search; it never proves which tool is active. Selection needs a unique tool with two separate plausible durability decreases. Camera movement triggers reacquisition. Name/type, capacity and durability history distinguish tools after they change screen position. Identical, conflicting or unreadable tools remain unconfirmed. Replacement tools require fresh use evidence. Brief confirmation reads are three seconds apart; confirmed monitoring follows the configured interval, capped at two minutes. When no labels are visible, discovery backs off rather than continuously OCRing the screen.

Only currently visible labels can be measured. Zooming a label off-screen or hiding it behind a window removes the measurement; the reader reacquires it when visible again. Moving the camera does not require recalibration. A previously automatic estimate pauses if its active tool can no longer be confirmed. Tool data cannot reveal furniture behind walls or names/durability that are not rendered by the game.

At most eight candidate labels are processed per pass, with a six-second OCR work budget and below-normal, single-thread workers. Cached crops are used between broad discoveries; failed crop locations trigger a new search in the same scan. No game input is generated. Screenshots remain transient in memory. The existing loot reader, saved history, optional sharing and manual planner-send controls are retained.

Automated tests cover multi-tool ambiguity, unrelated HUD fractions, damaged digits, missing labels, replacements, camera shifts, no initial region selection, and actual Tesseract reads of generated scenes. Real-world overlap/font/zoom coverage remains under validation; keep 1.11.1 as a known working fallback.

## rc.2 reliability and cost

Title masks detect invalid cached crop locations before numeric OCR. Fractions split across several OCR tokens receive one numeric crop. Verification uses two focused grayscale polarities; broad label mosaics and redundant mask retries are removed. Successful exact numeric pixels may reuse a verified result for eight seconds, capped at sixteen entries; no full images are cached. A single missed frame preserves identity evidence but reports no hidden active tool. Two misses clear wear evidence. Empty search delays are 3, 10, 30, 60, then 120 seconds; returning from a covered game immediately requests a new read.

Replay of three private saved game frames with real Tesseract, using the same tool-discovery source and captures: rc.1 used 5/13/17 calls, rc.2 used 5/5/5. All previously verified nonempty counters were retained; rc.2 also read an empty 0/3000 counter on the last frame. The difficult frames took about 1.02/0.99 seconds instead of 1.69/2.31 seconds on this PC. Two immediate unchanged repeats each used zero OCR calls and about 1 ms of reader work. The first discovery varied from 0.94 to 1.04 seconds. These are small sequential replay results, excluding screen capture and game FPS impact; cache savings apply only within its short TTL.

**SAVE STATUS** writes at most eight counter summaries and sixteen state transitions to a file you choose. The same bounded diagnostic summary is available read-only at `/tool-reader` on the paired local bridge, under its existing origin/Host restrictions. It contains no screenshots, capture boxes, game chat or profile paths. No website polling or extra process is added.

## rc.3 background check refinement

An installed-app check with the populated profile found higher idle CPU than the empty-profile benchmark. A private copy/profile trace led to repeated desktop-wide searches in background visibility checks. Game-window discovery now shares a bounded five-second cache; identities and live screen coverage still revalidate on every check. BDO in front bypasses cached misses immediately. A newly started game left in the background may take up to five seconds to be discovered. User-triggered tray and keyboard operations do not use this cache. Twelve consecutive unavailable checks measured 133 → 13 ms wall time and 125 → 16 ms CPU on this desktop; complete app CPU still depends on visible panels, profile and background work. Silver tables only update on changed content, preserving selection and one-second capture statuses.
