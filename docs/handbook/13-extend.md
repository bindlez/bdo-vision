# 13 · Recipes for extending Vision

## Add a new observed metric

Define the fact and its source first: for example, accepted rare-item units in the current grind session. Decide its session boundary, treatment of unpriced items and whether hidden periods count. Add a pure calculation or bounded ledger query. Test empty data, multiple sessions, repeated events and unknown values. Add the display to an existing refresh path and preserve optional sharing. Do not create a second ledger or recapture the screen just to render a metric already present in accepted events.

## Add another quest type

Start by collecting private examples of its heading, objective and counter layout. Extend objective scoping without weakening Guild/Daily/Bonus boundaries. Define a stable identity that cannot merge two unrelated objectives. Test both wrapped layouts and adjacent headings. Decide retention and alert behavior separately from OCR extraction. Add the new kind to the UI wording and handbook. A recognized counter must not automatically accept or turn in a quest in the game.

## Add a reader backend

Keep the existing observation contract: literal fields, geometry, capture time, confidence/consensus evidence and explicit unknowns. Put the backend behind a narrow adapter and replay the same annotated set through old and new readers. Measure latency, transient memory, cold start, recall and false positives. Package model/font data explicitly with provenance and a size budget. A native reader experiment is not automatically production-ready because it compiles.

Do not start by replacing the app, history or planner. Retain the old recognizer as a controlled comparison until the new one meets the relevant cases. Support cancellation and work deadlines. Test the shipped extracted build on a machine without the development environment before claiming no separate dependencies.

## Add a bridge route

Specify input/output fields, maximum body size, origin policy, enabled-feature requirement and failure responses. Add validation before domain work. Do not let the handler execute arbitrary commands, read arbitrary files or mutate Tk. Add malformed-body, foreign-origin and excessive-work tests as well as the success case. Keep `/durability` backward-compatible. Document the route in [the API guide](10-bridge-security.md).

## Add a native tab

Follow the feature controller pattern: initialize state in one owner, build widgets on Tk, run slow work off-thread, send results through `root.after`, use generation checks and stop scheduled callbacks on close. Reuse shared colors and controls. Present availability, freshness and errors in text. Make expensive functionality opt-in and keep all history writes in the correct ownership path.

## Add a planner chart

Use a bounded series from the existing domain calculation. Choose units, time range and excluded-time behavior before choosing colors. Handle no observations, no prices, partial totals and disconnected bridge states. Keep input escaped, preserve keyboard access and check reduced motion if adding animation. Avoid installing a chart framework for a graph that SVG or canvas can render with a few bounded points.

## Definition of done

A feature has an owner, a clear data contract, meaningful acceptance/rejection tests, a disconnected/unknown state, a performance budget, safe persistence and documentation. If it changes the shipped planner, test the embedded HTML. If it changes the Windows package, test the extracted package. If it depends on live BDO appearance, state which live setups were actually checked.
