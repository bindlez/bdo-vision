# 08 · Browser planner and build ownership

CP Intelligence assets are embedded by `python scripts/build_cp.py`. This updates the real inline planner and the standalone interactive CP demo. See [CP ownership, calculations and OCR](21-cp-intelligence.md) before changing exchange data or assumptions.

## What ships

`bdo-market-intelligence.html` is the real browser planner served by the desktop bridge. Its inline JavaScript is part of the shipped application. The `desktop/assets` directory also contains editable feature sources, JSON data and modules used by tests/build steps. Do not assume a source asset edit automatically updates the inline copy.

Gear Studio has explicit `VISION GEAR STUDIO START` / `END` markers. Edit `gear-planner.js` or `gear-planner.css`, then run `python scripts/build_gear.py` and inspect the resulting HTML diff. The generator embeds those assets into the main planner. For other sections, inspect their current embedding before changing either copy. There is not yet one universal frontend compiler that synchronizes every feature asset.

`scripts/check_planner.py` extracts the actual inline scripts from the main planner and demo HTML files and checks them with Node. `test_gear_core.js` validates equipment rules, while `test_planner_security.js` checks rendering of untrusted text, including Guild receipts. These are complementary checks; syntax validity does not prove the correct source copy was edited.

## State and origins

The browser stores planner, crafting and gear state in localStorage. The planner's legacy state uses its own keys; Crafting Studio uses `vision.craft.studio.v1`; gear uses `vision-gear-v1` and region-specific catalog caches. The generated contracts do not attempt to infer every JavaScript storage schema. Read the load/sanitize/save functions before modifying a key.

A browser origin includes protocol, host and port. Opening the same HTML as a file, on another localhost port or in another browser can appear to lose builds because localStorage is different. Export important state before changing hosting. Windows gear backups provide another recovery route but do not automatically back up every browser key.

## Rendering and updates

External market names and OCR objective strings are untrusted text. Use `textContent`, DOM creation or the established escaping helpers. Never concatenate a market name directly into an HTML fragment or an inline event handler. Keep graphs and point histories bounded. Update meaningful changes and use existing poll loops rather than adding a new interval per component.

Respect optional sharing. A timer that attaches to native loot should measure its own event range, not the user's lifetime totals. Preserve receipts for frozen/completed timers. Update Guild last-seen data as a snapshot, without generating quest progress in the browser.

## Demos

The offline crafting demo is generated by `scripts/build_crafting_demo.py` from the real planner with a synthetic adapter. It uses sample prices/drops and blocks network connections. It cannot see BDO, capture the desktop, restore the Windows tray or run global shortcuts. Keep demo storage keys separate from real keys. Rebuild the demo after changing the relevant planner UI and verify the sample label is still visible.

## A safe frontend feature recipe

Add pure rules in a small JS module where possible, test those rules with Node, integrate the rendering into the planner, regenerate the appropriate embedded block, check shipped inline syntax, then exercise the UI with both connected and disconnected bridge states. Do not treat a screenshot of sample data as live OCR validation.
